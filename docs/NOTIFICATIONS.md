# Alert notifications & integrations

CloudSecurity can push security events to **Microsoft Teams**, **Slack**,
**email** (SMTP or Azure Communication Services) and **signed webhooks**.
Admins configure channels and routing rules under **Notifications** in the UI;
analysts can see them (secrets masked) and the delivery log; viewers cannot.

## How it works

```
alert / finding / vuln / scan ──emit()──> notification_events      (same DB transaction as the alert:
attack-path poller ───────────┘             (inbox)                  nothing is lost, nothing blocks)
                                              │  dispatcher (leader replica only, every 5 s)
                                              ▼
                               rules: source, severity, subscription, tags, rule id, MITRE
                               dedup/throttle per group · quiet hours · daily digest
                                              │
                                              ▼
                               notification_deliveries (outbox + delivery log)
                                              │  retries with exponential backoff,
                                              ▼  dead-letter after N attempts
                               Teams · Slack · SMTP / ACS · signed webhook
```

* **Producers never wait for the network.** Detection, posture evaluation,
  scans and the API only insert one row into `notification_events`; a
  background dispatcher thread does the rest.
* **One sender.** Every replica / gunicorn worker starts a dispatcher, but only
  the holder of the `notification-dispatcher` leader lock (PostgreSQL advisory
  lock; a file lock on SQLite) works. If it dies, another replica takes over
  within one poll interval.
* **At-least-once.** A delivery that was being sent when the leader crashed is
  retried after a 5-minute lease. Receivers can de-duplicate on the delivery id
  (`X-CNAPP-Delivery` header / `id` field).
* **Event sources:** runtime alerts (new + optional status changes), posture
  findings (new, regressed, optional status changes), vulnerabilities (real
  CVE matches on laptops / Linux hosts are aggregated per CVE: one event "CVE-x in
  Google Chrome on 37 devices" for new critical or CISA KEV-listed CVEs, at most
  once per CVE per 24 h, group key `vulnerability:<CVE>:aggregate`; see
  [VULNERABILITIES.md](VULNERABILITIES.md)),
  attack paths (new confirmed paths, polled every 10 minutes; exposure paths
  without a confirmed weakness do not notify; the first poll records a
  baseline) and cloud scans (source `scan`, label "Cloud scans": completed /
  failed, manual or scheduled; the `trigger` attribute says which, and
  scheduled failures are titled "Scheduled <connector> scan failed").

## Configuration

| Variable | Default | |
|---|---|---|
| `NOTIFICATIONS_ENCRYPTION_KEY` | – | Fernet key encrypting channel secrets. **Required in production** (channels cannot be saved without it). Comma-separate several keys to rotate: the first encrypts, all decrypt; after prepending a new key run `python -m app.cli rotate-notification-key`, then remove the old one. Generate: `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` or `openssl rand -base64 32 \| tr '+/' '-_'`. In Azure it lives in Key Vault (`notifications-encryption-key`) and is generated by the deploy workflow. |
| `PUBLIC_BASE_URL` | – | URL users open the app at, e.g. `https://cnapp.example.com`. Used for "Open in CloudSecurity" deep links. Set automatically on Azure (the web app URL, or `CNAPP_PUBLIC_BASE_URL` / `infra/setup.sh --public-base-url` for a custom domain). |
| `NOTIFICATIONS_WORKER_ENABLED` | `true` | Run the dispatcher in this process (leader-elected). |
| `NOTIFICATIONS_POLL_SECONDS` | `5` | Dispatcher interval. |
| `NOTIFICATIONS_MAX_ATTEMPTS` | `6` | Attempts before a delivery is dead-lettered. |
| `NOTIFICATIONS_BACKOFF_BASE_SECONDS` / `_MAX_SECONDS` | `30` / `3600` | Exponential backoff (30 s, 1 m, 2 m, 4 m, … capped, ±20 % jitter; `Retry-After` honoured). |
| `NOTIFICATIONS_RETENTION_DAYS` | `30` | How long the delivery log and processed events are kept. |
| `NOTIFICATIONS_ATTACK_PATH_POLL_MINUTES` | `10` | Attack-path poll interval. |
| `NOTIFICATIONS_CONNECT_TIMEOUT` / `_READ_TIMEOUT` | `5` / `10` | Seconds, per request. |
| `NOTIFICATIONS_MAX_RESPONSE_BYTES` | `65536` | Larger responses are truncated (never buffered whole). |
| `NOTIFICATIONS_ALLOWED_HOSTS_<TYPE>` | see below | Host allowlist per type: `TEAMS`, `SLACK`, `WEBHOOK`, `ACS`. Comma-separated, `*.` = any subdomain, `*` = no allowlist. |
| `NOTIFICATIONS_SMTP_ALLOW_PRIVATE` | `false` | Allow an SMTP relay on a private (RFC 1918) address. |
| `NOTIFICATIONS_ALLOW_INSECURE_DEV` | `false` | **Development only** (ignored in production): allow `http://` and loopback/private targets, e.g. a local test receiver. |

Default allowlists: Teams `*.webhook.office.com, *.logic.azure.com, *.api.powerplatform.com`;
Slack `hooks.slack.com`; ACS `*.communication.azure.com`; generic webhooks: any public host.

**Outbound network (Azure Container Apps).** The backend calls the webhook
hosts on 443 and your SMTP server on 587/465 through the Container Apps
environment's default egress; the Bicep template deploys no firewall or NAT
gateway, so nothing extra is needed. If you route egress through Azure
Firewall / an NVA, allow those destinations (Teams: `*.webhook.office.com`,
`*.logic.azure.com`, `*.api.powerplatform.com`; Slack: `hooks.slack.com`;
ACS: `<resource>.communication.azure.com`). Receivers that allowlist source IPs
need a NAT gateway with a static IP on the apps subnet.

## Microsoft Teams

Teams retired Office 365 connectors in favour of **Workflows**; both work.

**Workflows (recommended)**
1. In the Teams channel: **⋯ → Workflows → "Post to a channel when a webhook request is received"**.
2. Pick the team/channel, finish the wizard and copy the URL
   (`https://prod-NN.<region>.logic.azure.com:443/workflows/...` or
   `https://<id>.environment.api.powerplatform.com/...`).
3. CloudSecurity → Notifications → **Add channel** → Microsoft Teams → paste the URL → **Send test**.

**Legacy incoming webhook connector**: channel → Connectors → Incoming Webhook →
copy the `https://<tenant>.webhook.office.com/webhookb2/...` URL.

Messages are Adaptive Cards (v1.4) with severity, source, resource,
subscription, rule, MITRE technique and an **Open in CloudSecurity** button.

## Slack

1. https://api.slack.com/apps → **Create New App** → From scratch → pick the workspace.
2. **Incoming Webhooks** → On → **Add New Webhook to Workspace** → choose the channel.
3. Copy `https://hooks.slack.com/services/T…/B…/…` into a Slack channel in CloudSecurity → **Send test**.

Messages use Block Kit (header, fields, button). Text from monitored
workloads is escaped, so it cannot `@channel` or inject links.

## Email: SMTP

Add channel → Email → provider **smtp**:

| Field | Example |
|---|---|
| SMTP host / port | `smtp.office365.com` / `587` |
| Transport security | `starttls` (587) or `tls` (implicit TLS, 465). Plain SMTP is not allowed. |
| Username / password | the mailbox or SMTP relay credentials (password stored encrypted) |
| From / Recipients | `cnapp@contoso.com` / `soc@contoso.com, oncall@contoso.com` (max 20) |

Certificates are verified against the hostname. Microsoft 365 needs SMTP AUTH
enabled for the sending mailbox; Gmail/Google Workspace needs an app password
(`smtp.gmail.com:587`). For an internal relay on a private IP set
`NOTIFICATIONS_SMTP_ALLOW_PRIVATE=true`.

## Email: Azure Communication Services

1. Create an **Email Communication Service** with an Azure-managed or custom
   domain, and a **Communication Service** resource; connect the domain to it.
2. Communication Service → **Keys** → copy the connection string
   (`endpoint=https://<name>.communication.azure.com/;accesskey=…`).
3. Add channel → Email → provider **acs**: sender `DoNotReply@<domain>`,
   recipients, connection string → **Send test**.

Requests are signed with ACS HMAC-SHA256 authentication; the delivery id is
sent as `Operation-Id`, so retries are idempotent.

## Signed webhooks

Each delivery is an HTTPS `POST` with a JSON body:

```json
{
  "id": "5f0c…",                       // delivery id (stable across retries)
  "type": "cnapp.notification.event",  // .event | .digest | .test
  "version": "1",
  "title": "Reverse shell detected", "severity": "critical",
  "link": "https://cnapp.example.com/threats?alert=…",
  "event": {"id": "…", "source": "runtime_alert", "type": "created", "severity": "critical",
            "title": "…", "summary": "…", "entity_id": "…", "asset_id": "…", "asset_name": "web-01",
            "subscription_id": "…", "rule_id": "CDR-001", "mitre_technique_id": "T1059.004",
            "occurred_at": "2026-10-15T12:00:00Z", "link": "…", "attributes": {}},
  "suppressed_since_last": 0
}
```

Headers:

| Header | |
|---|---|
| `X-CNAPP-Timestamp` | Unix seconds when signed |
| `X-CNAPP-Signature` | `v1=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>` |
| `X-CNAPP-Delivery` | delivery id, for de-duplication |
| `X-CNAPP-Event` | e.g. `runtime_alert.created` |

Verify against the **raw** body bytes, compare in constant time, and reject
timestamps older than 5 minutes (replay protection). Respond `2xx` quickly;
`408/425/429/5xx` and network errors are retried, other `4xx` and redirects are
not (redirects are never followed).

**Python (Flask)**

```python
import hashlib, hmac, os, time
from flask import Flask, abort, request

SECRET = os.environ["CNAPP_WEBHOOK_SECRET"].encode()
app = Flask(__name__)

def verify(body: bytes, ts: str, sig_header: str, tolerance: int = 300) -> bool:
    if not ts or not sig_header or abs(time.time() - int(ts)) > tolerance:
        return False
    expected = hmac.new(SECRET, ts.encode() + b"." + body, hashlib.sha256).hexdigest()
    return any(part.startswith("v1=") and hmac.compare_digest(part[3:], expected)
               for part in sig_header.split(","))

@app.post("/cnapp")
def receive():
    if not verify(request.get_data(), request.headers.get("X-CNAPP-Timestamp", ""),
                  request.headers.get("X-CNAPP-Signature", "")):
        abort(401)
    event = request.get_json()
    # de-duplicate on request.headers["X-CNAPP-Delivery"] ...
    return "", 204
```

**Node.js (Express)**

```js
const crypto = require("crypto");
const express = require("express");
const SECRET = process.env.CNAPP_WEBHOOK_SECRET;
const app = express();

function verify(rawBody, ts, sigHeader, toleranceSec = 300) {
  if (!ts || !sigHeader || Math.abs(Date.now() / 1000 - Number(ts)) > toleranceSec) return false;
  const expected = crypto.createHmac("sha256", SECRET).update(`${ts}.`).update(rawBody).digest("hex");
  return sigHeader.split(",").some((part) => {
    const [scheme, value] = part.trim().split("=");
    return scheme === "v1" && value && value.length === expected.length &&
      crypto.timingSafeEqual(Buffer.from(value), Buffer.from(expected));
  });
}

// express.raw keeps the exact bytes that were signed
app.post("/cnapp", express.raw({ type: "application/json" }), (req, res) => {
  if (!verify(req.body, req.get("X-CNAPP-Timestamp"), req.get("X-CNAPP-Signature"))) return res.sendStatus(401);
  const event = JSON.parse(req.body.toString("utf8"));
  // de-duplicate on req.get("X-CNAPP-Delivery") ...
  res.sendStatus(204);
});
app.listen(3000);
```

The signing secret must be at least 32 characters; the UI's **Generate**
button creates a random one, shown once before saving. To rotate: configure
the receiver to accept both secrets, update the channel, then drop the old one.

## Rules

A rule selects events and routes them to one or more channels. Nothing is
sent until at least one rule exists. A rule applies to events raised after it was
created (creating a rule never replays older alerts into a channel).

* **Match:** sources (empty = all), minimum severity, subscriptions, resource
  types, tags (`key=value`, `key=*` = present), detection/posture rule ids
  (wildcards, e.g. `CDR-00*`), MITRE techniques (`T1059` matches `T1059.004`).
  Events without a resource can carry `subscription_id`, `asset_type` and
  `tags` attributes (device events use `asset_type` = `device`).
* **Event types:** when exactly one source with several kinds of events is
  selected (e.g. *Endpoint device*), the rule builder lists its event types
  (none ticked = all).
* **Status changes:** off by default; tick *Also notify when an alert or finding
  changes status* to receive acknowledged/resolved/suppressed updates.
* **Throttling / dedup:** events are grouped (a detection rule on one resource,
  a posture rule on one resource, a CVE on one resource, …). A group is sent to
  a channel at most once per *throttle* window (default 60 min, 0 = every event);
  the next message says how many were suppressed.
* **Quiet hours:** e.g. 22:00–07:00 in `Europe/London`; messages are held (not
  dropped) until the window ends, except severities at/above the bypass level.
* **Daily digest:** instead of immediate messages, collect matches and send one
  summary per channel at the digest hour (rule time zone), worst first (top 50).
  Good for low/medium severity.

## Security

* **Secrets at rest:** webhook URLs (they are credentials), SMTP passwords,
  signing secrets and ACS connection strings are encrypted with
  `NOTIFICATIONS_ENCRYPTION_KEY` (Fernet: AES-128-CBC + HMAC-SHA256). The API
  never returns them; the UI shows masked hints (`https://hooks.slack.com/••••••`,
  `••••abcd`). Editing a channel without re-entering a secret keeps it.
* **Errors are redacted:** secret values (and URL paths/queries) are removed
  from delivery-log errors and logs.
* **SSRF protection for every outbound call:** https only; no credentials in
  URLs; per-type host allowlists; DNS is resolved once and **every** answer must
  be a public address (loopback, RFC 1918, link-local incl. `169.254.169.254`,
  Azure `168.63.129.16`, CGNAT, ULA `fc00::/7`, IPv4-mapped/NAT64/6to4/Teredo
  forms are all blocked); the connection is then pinned to that vetted IP (TLS
  still verifies the hostname), so DNS rebinding cannot redirect it; redirects
  are never followed; connect/read timeouts and a response-size cap apply.
* **RBAC:** admins manage channels and rules, send tests and retry dead
  deliveries; analysts have read-only access; viewers none. All changes are in
  the audit log (`notification_*` actions) without secret values.
* **Injection:** workload-controlled text is escaped for each format (Slack
  mrkdwn, Adaptive Card markdown, HTML email, header-safe subjects).

## Endpoint device events

The *Endpoint device* source ([device management](DEVICE_MANAGEMENT.md)) raises:

| Event type | Severity | When |
|---|---|---|
| `disk_encryption_off`, `firewall_off`, `antivirus_off`, `sip_disabled` | high | the issue appears on a check-in (first check-in, or it was not present at the previous one) |
| `av_signatures_outdated`, `os_updates_pending` (past the grace period), `gatekeeper_off`, `secure_boot_off` | medium | same |
| `screen_lock_off` | low | same |
| `stale` / `inactive` | medium / high | a device stops checking in (polled every 5 minutes by the dispatcher leader; the first poll only records a baseline). Notifies again if the device comes back and later goes quiet again |
| `command_succeeded` / `command_failed` / `command_rejected` | low / medium / medium | the agent reports the result of a remote action (lock device, collect logs, ...) |

Each event links to the device page, uses the issue code (or the command type)
as its rule id, so the *rule ids* filter works too (e.g. `firewall_*`,
`lock_device`), and is grouped per device and issue for throttling. Revoked
devices are not reported. Producing an event never fails a check-in.

## IT asset lifecycle events

The *IT asset lifecycle* source (`asset_lifecycle`, see [IT asset management](ASSET_MANAGEMENT.md)) raises:

| Event type | Severity | When |
|---|---|---|
| `retrieval_overdue` | medium | a leaver's asset is still *retrieval pending* after its due date (once per asset and due date) |
| `warranty_expiring` | low | the warranty ends within the warning window (default 30 days; once per asset and end date) |
| `device_unseen` | low | the asset's agent device has not checked in for the idle window (default 30 days); again if it returns and goes quiet again |
| `lost_or_stolen` | high | an asset is marked lost or stolen |

The first three are polled by the dispatcher leader every
`ASSET_NOTIFICATION_POLL_SECONDS` (1 hour). Events link to the asset page and
carry `asset_type` = `it_<type>` (e.g. `it_laptop`) for the asset type filter.

## Device approval events

The *Device approvals* source (`device_approvals`) covers the two-person approval
of high-risk device actions ([DEVICE_MANAGEMENT.md](DEVICE_MANAGEMENT.md#two-person-approval)):

| Event type | Severity | When |
|---|---|---|
| `approval_requested` | critical (wipe) / script risk | an admin requested a remote wipe or a medium/high-risk script: **a second admin must approve it** |
| `approval_approved` | high (wipe) / script risk | approved (for a self-approval: the cooling-off delay started) |
| `approval_rejected`, `approval_cancelled`, `approval_expired` | high (wipe) / script risk | decided, withdrawn, or no decision within `DEVICE_APPROVAL_TTL_HOURS` |
| `action_executed` | critical (wipe) / script risk | the command was queued for the device |
| `wipe_acknowledged` | critical | the agent confirmed it is about to wipe (the device may never report again) |

The events link to the **Approvals** page and carry `action`, `risk`,
`requested_by` and `decided_by`. Recommended rule: source *Device approvals*,
event types `approval_requested` + `wipe_acknowledged`, to the admins' Teams /
Slack channel or email, so a pending request is seen quickly.

## Server update events (on-prem)

The *Server updates* source (`server_update`) is raised by `cnapp-ctl update` on an
on-prem server ([DEPLOY_ONPREM.md](DEPLOY_ONPREM.md#6-updates-pull-based)), through
`python -m app.cli notify-server-update`:

| Event type | Severity | When |
|---|---|---|
| `update_rolled_back` | high | an update (manual or automatic) failed its health check and was rolled back automatically |
| `update_failed` | high | an automatic update failed (lookup, pull, timeout), or the rollback itself is not healthy |
| `updated` | info | an automatic update succeeded |

The events carry `from_tag`, `to_tag` and `automatic`. Recommended rule: source
*Server updates*, event types `update_rolled_back` + `update_failed`, to the admins'
channel. If the backend is down the event cannot be raised; the failure is then
only in `journalctl -u cnapp-update` and `/var/log/cnapp/auto-update.log`.

## Adding a new event source

```python
from app.notifications import Event, EventSource, emit, register_source

register_source(EventSource(name="device", label="Device posture",
                            event_types=("encryption_off", "stale"),
                            description="Endpoint agent posture issues"))

# wherever the issue is detected, inside the same DB transaction:
emit(db, Event(source="device", event_type="encryption_off", severity="high",
               title=f"Disk encryption is off on {device.hostname}", entity_id=device.id,
               group_key=f"device:{device.id}:encryption_off", link_path=f"/devices/{device.id}",
               attributes={"tags": device.tags, "asset_type": "laptop"}))
```

The source then appears in the rule builder automatically. Pull-based sources
pass `poll=` / `poll_interval=` (see `poll_attack_paths` in
`backend/app/notifications/builtin.py`). The endpoint device source in
`backend/app/notifications/device_source.py` is a complete example of both.

## Troubleshooting

| Symptom | Check |
|---|---|
| Nothing is sent | Is there an **enabled rule** that routes to the channel, and does the event meet its minimum severity? Delivery log empty = no rule matched. Notifications page → *Dispatcher*: one replica should be *Leader*; `NOTIFICATIONS_WORKER_ENABLED` must not be `false` everywhere. |
| "Send test" fails with *blocked: … allowlist* | The URL host is not in the type's allowlist (e.g. a Teams URL pasted into Slack). Adjust `NOTIFICATIONS_ALLOWED_HOSTS_<TYPE>` if you use a proxy/gateway. |
| *resolves to a blocked address* | The hostname resolves to a private/loopback/metadata IP. Use a public endpoint; for an internal SMTP relay set `NOTIFICATIONS_SMTP_ALLOW_PRIVATE=true`. |
| *HTTP 3xx: redirects are not followed* | Use the final URL (e.g. https instead of http, no URL shortener). |
| Teams `HTTP 400`/`404` | The workflow/connector was deleted or the URL is incomplete; recreate it. Workflows need a card payload: use the "Post to a channel when a webhook request is received" template. |
| Slack `invalid_token` / `no_service` | The webhook was revoked; create a new one. |
| SMTP *authentication failed* | Wrong credentials, SMTP AUTH disabled (Microsoft 365), or an app password required (Google). |
| ACS `HTTP 401` | Wrong access key, or the sender domain is not connected to the Communication Service. |
| *cannot be decrypted with the configured key(s)* | `NOTIFICATIONS_ENCRYPTION_KEY` changed. Restore the old key (append it after the new one to rotate), or re-enter the channel secrets. |
| `503 NOTIFICATIONS_ENCRYPTION_KEY is not configured` | Production without a key: set it (Key Vault on Azure). |
| Messages have no links | Set `PUBLIC_BASE_URL` (https). |
| Delivery stuck *pending* "held for quiet hours" | Expected: it is sent when the window ends. |
| Dead-lettered deliveries | See *last error* in the delivery log; fix the cause and press **Retry** (admin). |
| Too many messages | Raise the rule's throttle, raise the minimum severity, narrow by tags/subscriptions, or use a daily digest. |
